# CrazyArcade (BnB TW v22) — Complete Packet Catalog

## 1. Wire Framing, Cryptography & Primitive Encoding (` Confirmed `)

### 1.1 TCP Socket State (`CPacketSocket`, `0x005D82E1`, `0x00699B10`)

Upon `connect()`, `CPacketSocket` initializes with:
- `deg = 0`, `key = 0`, `hasKey = 0`
- `c1 = 0x66`, `c2 = 0xC0`, `c3 = 0xE7`
- `rxCounter = 40`, `txCounter = 40`, `rxStep = 3`, `txStep = 3`

#### Sequence Byte (`frame[0]`)
- **First S->C frame (Connect Hello, `deg = 0`, `hasKey = 0`)**:
  - Client extracts initial `key` from `frame[0]` (`sub_699AB0`):
    `key = (u8)((frame[0] ^ (c1 + (u8)rxCounter)) - c3)`
  - Sets `hasKey = 1`.
  - `CReceivedPacketConnect` is handled by `CPacketSocket::sub_699D60`, which advances the S->C receive counter exactly once: `rxCounter += rxStep` (`40 -> 43`). The first subsequent S->C degree-3 packet uses 43, then advances to 46.
  - Because `sub_696F60` (`CReceivedPacketConnect::Decrypt`) indexes `byte_924D10[256 * key + payload[0]]` (`16 x 256` table at VA `0x00924D10`, file offset `0x00524D10`), initial `key` MUST be in `0..15` (e.g., `key = 1` -> `frame[0] = ((1 + 0xE7) ^ (0x66 + 40)) & 0xFF = 0x68`).
- **Subsequent S->C frames (`deg = 3`, `hasKey = 1`)**:
  - Client verifies `frame[0] == (u8)(((u8)key + c3) ^ (c1 + (u8)rxCounter))`
  - `rxCounter += rxStep` (`+3` per packet).
- **C->S frames (`deg = 2`)**:
  - Client writes `frame[0] = (u8)(((u8)key + c3) ^ (c2 + (u8)txCounter))`
  - `txCounter += txStep` (`+3` per packet).

#### Frame Layouts by Degree (`deg`)
1. **Degree 0 (`CReceivedPacketConnect`, S->C Connect Hello, `N + 3` bytes)**:
   - `frame[0]`: Sequence byte (encodes initial `key` in `0..15`)
   - `frame[1..2]`: `u16 BE` payload length `N` (unscrambled)
   - `frame[3..3+N-1]`: Connect Hello payload (`payload[0]` = `byte_924D10` inverse lookup of `plain[0]`)
2. **Degree 2 (`CSendPacket` at `0x0057B5A4`, C->S TCP packets, `N + 5` bytes)**:
   - `frame[0]`: Sequence byte
   - `frame[1]`: Random pad byte
   - `frame[2..3]`: `(N ^ 0xA569)` in Big-Endian (`u16 BE`)
   - `frame[4..4+N-1]`: Stream-cipher encrypted payload (`sub_695B00(txCounter, cipher, plain, N)`)
   - `frame[4+N]`: `CCRC8::Compute((u8)txCounter, plain, N)`
3. **Degree 3 (`CReceivedPacketBase`, S->C TCP packets, `N + 7` bytes)**:
   - `frame[0]`: Sequence byte
   - `frame[1]`: Random pad byte
   - `frame[2..5]`: `(N ^ 0x96CA5395)` in Big-Endian (`u32 BE`)
   - `frame[6..6+N-1]`: Stream-cipher encrypted payload (`sub_695B00(rxCounter, cipher, plain, N)`)
   - `frame[6+N]`: `CCRC8::Compute((u8)rxCounter, plain, N)`

#### Payload Stream Cipher (`sub_695B00` / `sub_695BA0`)
- Given `counter` (`txCounter` or `rxCounter` before the post-frame `+3` step) and plaintext `src[0..N-1]`:
  - `k = (counter ^ 0x53351D9C) >>> 0`
  - `words = Math.floor(N / 4)`
  - If `words > 0`:
    - `dstU32LE[0] = (k ^ srcU32LE[0]) >>> 0`
    - For `i = 1 .. words - 1`:
      - `k = (k - 0x63CAACE3) >>> 0` (decompilation: decimal `1674226915`; CA.exe immediate at `0x00695B46` / `0x00695BE7`)
      - `dstU32LE[i] = (k ^ srcU32LE[i] ^ srcU32LE[i - 1]) >>> 0`
    - `tailKey = srcU32LE[words - 1]`
  - Else (`words == 0`):
    - `tailKey = k`
  - Remaining `N % 4` tail bytes at `offset = words * 4`:
    - `dst[offset + b] = src[offset + b] ^ ((tailKey >>> (8 * b)) & 0xFF)`

### 7.2 UDP Framing, Load Registration & Gameplay (`MTUDPPeer`, `CUDPPeerMan`, `CGameStage::sub_4ECF93`)

- **Outer Frame (`MTUDPPeer` at `0x005EBFA0`)**:
  `[u8 L = 1 + innerLen][innerPayload (deg 0 plain BE)][u8 CRC8(0, frame[0..L-1])]`. Since `L` is one byte, `innerLen` is at most 254 bytes. `sub_693100` (`0x00693100`) builds this length byte and rejects ordinary input lengths where `a3 + 1 > 0xFF`; the TypeScript encoder now rejects payloads above the representable limit instead of wrapping the length.
  - The Client receive loop `MTUDPPeer::sub_5EBF73` (`0x005EBF73`) walks concatenated chunks in one UDP datagram and stops at the first malformed chunk. The send helper `sub_693100` (`0x00693100`) wraps one payload and issues one `sendto` per call; therefore receive-side batch support does not establish that Client requests are batched. The server's inbound dispatcher requires a single frame per datagram, matching the observed Client send path.
- **Unverified keepalive candidate and local reply policy**:
  - The server model accepts a `6B` inbound candidate `[u16 BE(0), u32 BE(userId)]`. The checked-in `CA.exe.c` does not contain the previously attributed `sub_57BEAE` / `sub_57BDCE` bodies, so no Client sender, direction provenance, or cadence is established.
  - The model replies with a `1B` inner payload `[u8(4)]`. `CUDPPeerManBase::sub_5EC943` proves that the Client recognizes this one-byte type, not that a production server sends it in response; verify both sides with a capture.
- **Game Load Registration (`sub_4ED400` at `0x004ED400`)**:
  - Client sends `36B` inner payload every 1s during `CGameStage` loading:
    `[u16 BE(1), u32 BE(userId), u16 BE(roomId), u32 BE(roomGameKey), u32 BE(ip0), u16 BE(port0), u32 BE(ip1), u16 BE(port1), u32 BE(mapCrc8), 4B(p0Attrs), 4B(p1Attrs)]`.
  - `sub_5EBBD6` obtains at most two local IPv4 addresses via `gethostname` / `gethostbyname`; `sub_4ED400` pairs each non-zero address with the client's UDP listening port and leaves missing candidates as `0.0.0.0:0`. The reconstruction preserves those two client-supplied candidates verbatim.
  - **Room-context dataflow cross-check:** the `u32` represented here as `roomGameKey` is serialized from Client global `j[92]`. Lobby response/room-record handlers populate that word alongside the room number; `sub_4C7D37` compares an invite's received word to room-record `+68` before entering the C->S 76 writer, and C->S 21 writers use the same pair. S->C 113's `sub_4D9F8A` has no direct `j[92]` assignment, and `sub_4ED400` places `j[92]` immediately after the UDP room ID. This proves Client-side value reuse, not a slot identity, secret/challenge, or official-server equality check. The reconstruction's lobby builders currently put `room.chiefSlotNetId` in these room-context positions, a local model choice; the UDP handler does not validate this field pending clearer evidence about the context word's stability and purpose.
  - `sub_4F2065` consumes three `(ip, port)` candidates per peer slot. Because the client registration packet supplies only two, this server reconstruction fills candidate three from the UDP datagram's observed source IPv4 address/port. This is a high-confidence inference from the client schemas, not a captured production response; validate NAT traversal against a live network. Missing or unsupported IPv4 routes remain `0.0.0.0:0` rather than being replaced with loopback; the client's `sub_693B50` returns no peer for a zero IP or port.
  - The `S->C 135` relay endpoint is the configured GameServer UDP address (`PUBLIC_IP` plus `GAME_UDP_PORT`); it must not use the local bind address `HOST` unless that address is reachable by the client.
  - Client code proves the 36-byte writer and retry/stop conditions, but not the official server's length policy, identity association, or interpretation of `mapCrc8` and the two attribute blocks. This reconstruction requires exactly 36 bytes, an active room, and a matching occupied slot owned by the current GameServer session before changing state; truncated `12..35B` prefixes are rejected.
  - The local server sends `S->C 136` (`[u8 slotIdx]`) only when an owned slot first becomes loaded, then broadcasts `S->C 135` (`sub_4F2065`) once when all occupied slots are loaded. Identical UDP retries do not repeat either packet or reset the clock. Later valid registrations can update the server's relay target/candidate state, but the reconstruction does not resend `S->C 135` after match setup; the official server's duplicate and endpoint-refresh policy is unknown.
- **P2P / Relay Gameplay Packets (`CUDPPeer` `0x0057B482` -> `CGameStage::sub_4ECF93` `0x004ECF93`)**:
  - `CUDPPeerClient::sub_5EC195` emits a 3B peer-control envelope `[u8(0), u8(0), u8(localPeerIdx)]`; companion `sub_5EC1FF` emits `[u8(0), u8(1), u8(localPeerIdx)]`. `CUDPPeerManBase::sub_5EC943` routes envelope type `0` using the second byte and does not consume the third byte on that branch.
  - The reconstructed GameServer answers the observed `[0, 0, peerIdx]` probe with `[0, 1, peerIdx]`. This is a local response choice; the Client itself also emits the same `[0, 1, idx]` shape from `sub_5EC1FF`, so that shape alone does not prove a server reply.
  - Peer gameplay data is wrapped as `[u8(1), u8(senderPeerIdx), gamePayload]`; `sub_5ECA87` fans out and `sub_5ECB1E` targets one peer. The Client receiver's `sub_5EC943` removes the first two bytes, then `CGameStage::sub_4ECF93` dispatches on an inner `u16` code. These inner codes are a separate namespace from TCP `ClientOpcode` / `ServerOpcode` and from the peer-envelope type:
    - `inner code 0` (`8B` total): `[u16(0), u8 contextCheck, 4B LE packed {slot:4 bits, x:10 bits, y:10 bits, stateByte:8 bits}, u8 sequence]`.
    - `inner code 1` (`13B` total): `[u16(1), u8 contextCheck, u8 slot, u8 stateCheck, u8 field, u16 field, u16 field, u8 field, u8 field, u8 field]`.
    - `inner code 2` (`9B` total): `[u16(2), u8 contextCheck, u8 index, u8 field, u16 field, u16 field]`.
    - `inner code 3` (`26B` total): `[u16(3), u8 contextCheck, 4B LE packed {slot/x/y/stateByte}, 16B opaque block, u8 field, u8 field, u8 sequence]`.
    - `inner code 4` (minimum `5B`): `[u16(4), u8 stageContext, u16 objectKey, opaque tail]`; the Client looks up the object and delegates the remaining reader to its virtual handler.
  - The code/length associations and scalar read widths above come from `sub_4ECF93` / `sub_57A288` / `sub_579EA0`. Field meanings remain UNKNOWN unless explicitly packed as bits; do not infer packet names from the inner numeric codes.
